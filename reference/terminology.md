# 文件閱讀與名詞基準

## 快速理解

| 先問自己 | 文件直接回答 |
| --- | --- |
| Why（為什麼要看這頁） | 「前端／後端」和「前台／後台」描述的是兩種不同分類；「串接／整合／共用」也不是同一種工作。名詞混用時，讀者會誤判誰負責資料、誰可以修改，以及這次工作應放在哪個 Repository。 |
| What（現在實際固定什麼） | 本頁定義四個核心詞、5＋1 系統、Repository／專案／Area、串接與整合、資料表／Entity／DTO／ViewModel、圖片／媒體／地點，以及 Balance、Transaction、Batch、Audit log 的差別。每個詞都對應 QMAH 的實際專案或資料表。 |
| How（單獨讀一頁時怎麼用） | 讀到會影響該頁判斷的術語時，在第一次出現處看括號內的台灣繁中說明；要確認完整邊界就回本頁查表。程式識別字、API path、欄位、Schema、狀態值和命令維持原文，先看 Balance、Transaction、Batch 或 Audit log 分別在回答哪一種問題。 |

**適用情境：** 閱讀者只開啟某一個 API、系統或資料表頁面，卻不確定「前台／後台」、「後端／前端」、「流水／稽核」或「共用／跨系統」的意思時，直接在本頁找到詞的邊界，不需要先讀完整文件站。

本頁是跨文件共用的名詞基準。每份文件仍須能獨立閱讀；第一次出現、而且會影響理解的技術名詞，會以「原文（台灣繁體中文說明）」補充。完整定義集中在本頁，程式識別字、資料表名稱、API 路徑、欄位與狀態值則維持原文。

## 先分清四個核心詞

「前端／後端」描述技術層；「前台／後台」描述使用對象。四者不是同義詞，也不是四個獨立 Repository。

| 名詞 | 白話定義 | QMAH 對應 |
| --- | --- | --- |
| 後端（backend） | 在伺服器執行驗證、規則、資料存取與檔案處理的程式 | `QMAH.Api`、`QMAH.Infrastructure`，以及 `QMAH.Web` 內的伺服器端 Controller 與 Service |
| 前端（frontend） | 在瀏覽器呈現畫面、接收操作並呼叫後端的程式 | `QMAH.Client` 的 Angular，以及 `QMAH.Web` 產生的 Razor、HTML、CSS 與 JavaScript |
| 使用者前台（front office） | 一般訪客與會員使用的產品介面 | `QMAH.Client` Angular 前端呈現的介面 |
| 管理後台（back office） | 管理員、內容編輯與營運人員使用的管理介面 | `QMAH.Web` Razor 前端呈現的管理介面 |

因此，`QMAH.Web` 同時是後端主機與管理後台的前端來源；`QMAH.Client` 是使用者前台的前端，呼叫 `QMAH.Api` 後端。文件使用「前台」時，指使用者產品介面；使用「後台」時，指管理介面，不把兩者混稱為同一件事。

## 5＋1 系統怎麼稱呼

QMAH 的五個功能系統與一個跨系統營運入口如下：

| 類別 | 系統 | 主要責任 |
| --- | --- | --- |
| 功能系統 | Catalog（圖鑑） | 文物、分類、年代、來源、授權、題庫關聯與解鎖 |
| 功能系統 | Game（遊戲） | 房間、回合、作答、投票、邀請、Mini Game 與結算 |
| 功能系統 | Social（社群） | 貼文、留言、檢舉、活動、報名、通知與社群媒體 |
| 功能系統 | Store（商城） | 商品、購物車、訂單、付款、庫存、折價券與點數 |
| 功能系統 | User（會員） | Identity 帳號、會員資料、地址、登入活動、成就與稱號 |
| 跨系統入口 | 營運中心（Operations） | 讀取各系統資料做統計，並執行有原因、有流水的管理與批次操作 |

Shared（共用基礎）不是第六個業務系統。它是文件上的共用入口；`QMAH.Infrastructure` 是共用程式庫；`common` Schema 是共用資料表的資料庫分區。三者都不會取代上述五個功能系統或營運中心的資料主責。

## 系統、Repository、專案與 Area

| 名詞 | 用途 | 例子 |
| --- | --- | --- |
| 系統 | 以業務責任劃分的功能範圍 | Catalog、Game、Social、Store、User、Operations |
| Repository | Git 儲存庫，保存一組程式、文件或資料交付物 | `QMAH`、`QMAH-Docs`、`QMAH-Database` |
| 專案（project） | Repository 內可建置或執行的程式單位 | `QMAH.Api`、`QMAH.Web`、`QMAH.Client`、`QMAH.Infrastructure` |
| Area | `QMAH.Web` 內的管理後台路由與檔案邊界 | `Areas/Catalog`、`Areas/Game`、`Areas/Store` |

跨系統引用不代表移轉資料主責。需要共用規則時，透過 API、明確 Service、外鍵或目前登入身分連接；資料仍由原本負責的系統維護。

## 「串接」、「整合」與「共用」的差別

| 用語 | 使用時機 | 例子 |
| --- | --- | --- |
| 串接 | 一個程式依契約呼叫另一個程式或外部服務 | Angular 串接 `/api/v1`；地圖連結串接地址與座標；測試工具串接 Scalar |
| 整合 | 多個資料責任在同一條流程中協同完成 | 建立訂單時整合商品、庫存、折價券、點數與付款狀態 |
| 共用 | 多個入口重用同一個通用元件或服務 | API 與 Web 共用 `QmahMediaUrlResolver`；多個流程共用資產流水服務 |
| 跨系統確認 | 在不移轉主責的前提下，核對兩邊的識別碼、狀態與錯誤行為 | Game 使用 Catalog 的 `ArtifactId`，結算後再由資產服務寫入點數或鑰匙 |

「串接」通常回答「誰呼叫誰、送什麼、收到什麼」；「整合」還要回答「多張資料表如何一起成功、失敗如何回復、歷史如何追溯」。

## 資料表、Entity、DTO 與 ViewModel

| 名詞 | 白話定義 | 使用邊界 |
| --- | --- | --- |
| 資料表（table） | SQL Server 實際保存資料的結構 | 以 `Schema.sql` 與 QMAH-Database Snapshot 為準 |
| Entity（資料庫對應模型） | 後端用來對應資料表、由 ORM（物件關聯對映工具）追蹤的程式模型 | 留在後端與資料存取層，不直接交給使用者前台 |
| DTO（API 對外傳輸的資料格式） | API 傳給前台或接收前台輸入的資料結構 | 由 API 契約定義；前台依欄位與狀態使用 |
| ViewModel（畫面模型） | Razor 管理後台單一頁面需要的輸入或顯示資料 | 由 `QMAH.Web` 的 View 與 Controller 使用 |

前台不從 Entity 或資料表猜欄位；後台表單也不把整個 Entity 當成可任意修改的輸入模型。要查對外欄位時看 [REST API 契約](./rest-api.md)，要查 SQL 結構時看 [資料表參考](../architecture/database-reference.md)。

## 圖片、媒體與地點

「圖片」是使用者看見的影像內容；「媒體」是較大的技術範圍，還包括檔案識別、替代文字、權限、儲存來源與公開網址。文件談檔案來源、`Media` 設定或 CDN 時使用「媒體」；談畫面中的影像時使用「圖片」。

地圖不是 QMAH 保存的圖磚資料。QMAH 保存活動、貼文或會員地址需要的文字地點與可選座標；地圖服務只負責顯示、搜尋或選點。相關說明見[地點與地圖串接](../features/map-integration.md)與[媒體交付設定](../frontend/media-delivery.md)。

## 資產、流水、批次與稽核

| 名詞 | 用途 |
| --- | --- |
| 資產 | 會員持有且會增減的點數、鑰匙或優惠券 |
| Balance（餘額） | 某一時間可快速讀取的目前數量，不單獨代表異動原因 |
| Transaction（流水） | 一次增加、扣除、消耗、兌換或回復的不可任意改寫歷史 |
| Batch（批次） | 同一個活動或管理操作的條件、原因、操作者與處理結果 |
| Audit log（稽核紀錄） | 管理操作入口、操作者、目標與結果的操作紀錄，不等於資產流水 |

資產目前有多少看 Balance；為什麼改變看 Transaction；一批活動影響多少人看 Batch；管理員從哪個管理入口做了什麼看 Audit log。四種資料各自回答不同問題，不以一張表取代全部歷史。

## 文件的標題與查閱方式

文件站的標題採固定語意，讓搜尋結果、側欄與頁內內容可以互相對應：

| 目的 | 統一使用的標題 | 內容 |
| --- | --- | --- |
| 先知道頁面能回答什麼 | 快速查閱 | 一眼找到入口、責任與常見查詢 |
| 先掌握頁面重點 | 快速理解 | 用 Why（為什麼）、What（目前內容）、How（怎麼使用）三列交代要解決的工作、實際責任與查詢／修改起點 |
| 了解程式實際怎麼跑 | 實際運作方式 | 以一次請求或一條業務流程說明資料如何流動 |
| 知道誰能改什麼 | 開發規則與跨系統界線 | 主責、引用、授權、交易與歷史保留 |
| 開始做使用者前台 | 前台接手建議 | API 組合、畫面狀態、錯誤與跨系統確認 |
| 需要精確契約 | 查詢入口／後續查閱 | 連到唯一的 API、資料表、工具或操作文件 |
| 需要照步驟完成單一任務 | 操作流程 | 只表示這一項操作的依賴，不表示五個功能系統與營運中心的開發先後 |

文件排列是查找路徑，不是開發排程。五個功能系統與營運中心可以平行開發；只有共同識別碼、API 回應、資料庫限制或跨表結算需要在整合點互相確認。

## 名詞第一次出現的規則

每份文件都以獨立閱讀為前提：

1. 會影響這一頁理解的術語，在該頁第一次出現時補上簡短括號說明。
2. 同一術語的完整定義只放在本頁；其他文件以連結回來，避免每頁各自創造不同說法。
3. API 的 `summary`（清單短摘要）只說明用途；`description`（完整行為說明）直接交代輸入、輸出、權限、流程條件與錯誤。
4. 程式碼、命令、路徑、資料表、欄位、API 路徑與狀態代碼不翻譯、不改寫；必要的白話解釋放在程式碼外。

相關的 API 專有名詞集中在[API 名詞表](./api-glossary.md)；文件維護規則見[QMAH-Docs 協作規則](../CONTRIBUTING.md)。
